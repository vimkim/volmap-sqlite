# Volmap SQLite Inspector v1

Status: ready-for-agent

## Problem Statement

Engineers and operators can use SQLite itself to query a healthy logical database, but they do not have a focused way to navigate the physical main-file image, understand how schema objects reach their B-trees and pages, or retain trustworthy evidence when storage is damaged. General database browsers emphasize tables and query results, while low-level tools tend to expose bytes without a coherent, snapshot-scoped model. That leaves users unable to answer basic physical questions—what role a page has, which validated relationship reaches it, where a malformed traversal stopped, whether adjacent sidecars make the main file stale, and what evidence remains usable—without writing one-off tooling or accidentally changing, recovering, or broadly disclosing database contents.

Volmap SQLite Inspector v1 must make those answers navigable while remaining honest about its limits. It must inspect only frozen inputs, treat the physical main-file image as distinct from the logical database image, preserve independently valid evidence from damaged or hostile files, scale beyond memory-sized databases, and disclose typed application values only after the operator explicitly selects one cell. Its web and terminal interfaces must project the same inspection graph without forcing physical, semantic, and keyboard-oriented workflows into one compromised layout.

## Solution

Build a standalone, read-only `volmap-sqlite` executable that accepts a frozen SQLite database snapshot, directly parses its physical main-file image into a normalized inspection graph, and presents that graph through an embedded browser viewer or focused terminal interface. The fast inspection performs a complete, unsampled structural pass within explicit operational budgets. It records database geometry, the page inventory, page-role claims, allocation structures, B-tree topology, cell boundaries, schema attribution, sidecar evidence, diagnostics, and inspection coverage. Malformed structures stop only at their validation boundaries and retain their validated prefixes unless database geometry itself is too untrustworthy for broader inspection.

The browser opens on a page atlas: a complete physical mosaic linked to page evidence, cells, diagnostics, and semantic ownership. A separate schema flow shows each schema object's validated path through its root B-tree to descendant pages and cells, while rootless schema objects remain visible without invented storage. The TUI provides a dense, keyboard-oriented terminal inspection flow from database-level schema or allocation entry points to a page and an optional selected cell. All projections share entity identity, selection, warnings, coverage, and revision semantics.

Deep inspection is an explicit, bounded action on one selected cell. It reconstructs that cell's local and overflow payload, decodes typed application values when valid, withholds raw application payload bytes, and publishes the added evidence as a new immutable inspection revision. The web server is local and path-private by default, supports an explicit non-loopback listener with a prominent warning, performs no telemetry or external calls, and ships with the browser assets in the same binary.

## Implementation Decisions

- The product is a standalone SQLite-focused sibling of Volmap, not a shared multi-engine implementation. It adopts the established concepts of read-only inspection, an inspection graph, evidence-backed diagnostics, and inspection adapters, but common code is extracted only after stable cross-engine abstractions emerge.
- Version 1 ships one executable built around a Rust 2024 core with unsafe code forbidden. The same artifact contains the Crossterm TUI, the Axum/Tokio HTTP adapter, the React/TypeScript/Vite browser viewer, static browser assets, and the optional bundled-SQLite metadata-helper subcommand. Dependencies and frontend tooling are pinned.
- The central application boundary is a snapshot-scoped inspection session. It accepts a source plus operational budgets, emits deterministic fast-inspection progress, publishes an immutable inspection graph revision on completion or explicit stop, resolves typed entity selectors, and accepts bounded deep-inspection requests that may publish later revisions.
- A database snapshot consists of the accepted frozen main-file bytes and the observed adjacent sidecar set. Input identity and file metadata are checked before and after inspection work; any observed change invalidates the snapshot. Already observed facts remain diagnostic evidence, but no further enrichment is accepted and the result is not represented as coherent.
- Version 1 does not acquire a live-consistent copy, follow a changing database, coordinate with a running SQLite process, or refresh a snapshot in place. Operators are responsible for supplying a stopped database, immutable snapshot, or otherwise stable copy.
- The direct, bounds-checked Rust parser is the sole authority for physical evidence, byte coordinates, entity identities, relationships, diagnostics, schema attribution, and explicitly selected stored values. Input-derived arithmetic and ranges are checked before reads or allocation.
- The fast inspection derives database geometry from validated header fields and then scans the complete page range without sampling. It inventories page boundaries and role claims; B-tree topology and cells; freelist trunks and leaves; overflow links; pointer-map entries where applicable; the lock-byte page where present; schema attribution; unknown or conflicting pages; sidecar evidence; diagnostics; and coverage.
- A page role is a classification supported by local structure, validated inbound or outbound relationships, or both. Conflicting valid claims are retained as conflicts rather than collapsed into one owner-like label. Unsupported readable bytes remain opaque evidence.
- The inspection graph is normalized and independent of presentation. At minimum, it represents the database snapshot, immutable inspection revisions, pages, cells, schema objects, physical evidence with byte coordinates and named validation rules, relationship claims and validated relationships, sidecar evidence, diagnostics, operational-budget stops, and inspection coverage.
- Entity identity is typed and scoped to one database snapshot. A page identity is its one-based page number; a cell identity is its page number plus physical cell index. Schema names, decoded rowids, keys, values, URLs, and textual selectors are interpreted attributes or adapter addresses, never replacement identities.
- Validation is boundary-based. A failed prerequisite prevents only dependent interpretation and traversal. The graph retains the source claim, its coordinates, every consecutively validated member before the failure, independently validated parents and siblings, and a diagnostic describing the stopping boundary. Only geometry that cannot safely establish page boundaries prevents broader inspection.
- Diagnostics use stable machine-readable codes and carry severity, affected entity or relationship, supporting evidence, and containment or coverage impact. Human wording may evolve without becoming an API contract. Budget exhaustion and cancellation are coverage stops, not corruption diagnostics.
- Fast inspection is structurally complete within its recorded coverage: it may stop because of cancellation, invalid geometry, a failed validation boundary, or an operational budget, but it never samples and then labels the result complete. The effective budgets and exact stopping reason are part of the published graph.
- Potentially unbounded work is cancellable and governed by explicit configurable ceilings, including memory, concurrency, traversal depth, linked-chain length, cell count, reconstructed payload bytes, decoded value bytes, request size, and response size. Concrete defaults and performance thresholds are selected from reproducible benchmarks rather than guessed in this specification.
- Multi-gigabyte support uses positional file access, bounded caches, streaming iteration, and spillable indexes where necessary. The main file and decoded payload population are never held in full solely to simplify implementation.
- Version 1 presents only the main-file image. It discovers adjacent WAL, rollback-journal, and shared-memory files and parses only supported structural metadata needed for disclosure. It does not apply WAL frames, checkpoint, roll back a hot journal, reconstruct a logical database image, or treat the WAL-index as authoritative.
- Sidecar evidence distinguishes presence, type, readable metadata, validation state, and interpretation consequence. WAL presence warns that committed frames may not be reflected in the main file. A rollback journal that satisfies the supported hot-journal evidence checks warns that ordinary SQLite opening could roll it back. Shared memory is explicitly labelled a non-authoritative coordination/cache artifact.
- Fast inspection may decode record headers, serial types, cell boundaries, rowids or keys needed for structure, and schema records required for attribution. It does not retain or publish broad application values. Raw application payload bytes are never included in graph responses, diagnostics, logs, search indexes, URLs, or fallback renderings.
- Deep inspection requires a typed selector resolving to exactly one cell in the current database snapshot and base revision. It runs asynchronously under its own budgets, validates and reconstructs only that cell's local payload and overflow-chain prefix, decodes typed values where supported, records exact coverage, and publishes a new immutable revision only when a coherent result is ready.
- An immutable revision never changes after publication. Later deep inspection adds evidence without changing existing page or cell identities. A request against an invalidated snapshot is rejected; a failed, cancelled, or stopped enrichment leaves prior revisions intact and returns its coverage outcome without implying success.
- Explicit-target disclosure is enforced below all adapters at the inspection-session/query boundary. Only the selected cell's typed application values may be returned, and only in a response explicitly scoped to that cell and revision. Structural facts and semantic metadata remain broadly navigable. Undecodable data is described structurally; it is never exposed as raw bytes.
- Schema attribution is built from directly parsed schema records and validated root-page/B-tree relationships. Schema metadata is descriptive enrichment and cannot override physical facts. Views, triggers, and virtual tables without a directly attributable storage B-tree are represented as rootless schema objects; no extension or virtual-table module is executed.
- A resource-limited private subcommand may use the bundled SQLite library to enrich a sidecar-free private copy with fixed, read-only schema-metadata queries. It never queries application tables, loads extensions or virtual-table modules, or receives authority over physical facts. It runs with trusted-schema behavior disabled, tight limits, and unavailable-result fallback; failure affects only semantic metadata.
- The default web workspace is the page atlas validated by prototype Variant A. It presents the complete physical page mosaic, a role/finding legend, snapshot geometry, fast-inspection coverage, sidecar disclosure, semantic entry points, and a selection-linked evidence panel for the active page and cell.
- Schema-object navigation is a separate schema flow validated by prototype Variant B. It explicitly lays out schema object to validated root B-tree to descendant pages and cells, includes a physical landing/detail view, and represents rootless objects as declaration-only rather than failed attribution.
- The page atlas and schema flow share one adapter selection model keyed by entity selectors. Selecting a schema object may land on its root page; selecting a page shows any validated schema attribution; selecting a cell preserves its containing page. Switching projections preserves resolvable selection and never creates adapter-specific entity identities.
- Page detail includes structural facts, role claims, byte coordinates, a structural byte map, cell inventory, relationships, diagnostics, coverage, and semantic attribution. Application values appear only in the selected-cell deep-inspection result.
- The TUI follows prototype Variant C as a dense terminal inspection flow rather than mirroring the web layout. It provides keyboard traversal from database-level schema or allocation entry points to page and cell, a visible navigation path, an evidence pane, diagnostics, coverage, sidecar state, revision state, command help, and an explicit deep-inspection action.
- Browser and TUI projections reuse the inspection-session queries and view models needed to render the shared graph; they do not read database bytes or derive storage truth. Presentation-only state such as active workspace, focus, filters, and expanded panels remains adapter-local.
- Web routes and API requests are scoped to one web inspection session, opaque source identity, snapshot, and revision. They use typed selectors rather than absolute paths or decoded values. Responses do not expose absolute source paths. A separate sanitized display name may be shown to the operator.
- The embedded server binds to loopback by default. An explicit listen address permits a non-loopback bind and emits a prominent warning that the service provides no authentication or TLS. Internet-facing deployment requires operator-controlled protection or a trusted reverse proxy and is not a built-in product mode.
- Browser delivery and APIs are same-origin. Inspection responses are non-cacheable and use strict security headers; request and response sizes are bounded. The executable performs no telemetry or external network calls.
- The throwaway navigation prototype is not production code and is not merged or promoted. Production interfaces are rewritten from its validated information architecture. ADR-0015 and prototype verdict commit `dc2062b` are the decision records when visual details need clarification.

## Testing Decisions

- The primary behavioral seam is the highest shared seam: the snapshot-scoped inspection-session boundary. Tests feed frozen database and sidecar fixtures into a session, observe progress and publication, query the resulting inspection graph through typed selectors, request deep inspection, and assert externally visible revisions, evidence, diagnostics, and coverage. They do not assert private parser types, cache layout, traversal helpers, frontend component structure, or internal indexing strategy.
- Parser-focused unit and property tests remain appropriate below that seam for byte arithmetic, varints, payload distribution, page headers, record serial types, checksums, and other format primitives where exhaustive boundary conditions are clearer than application-level scenarios. These tests support the primary seam rather than becoming an alternate behavioral contract.
- A canonical fixture corpus covers valid databases across supported page sizes, encodings, schema formats, rowid and WITHOUT ROWID tables, interior and leaf table/index B-trees, freelists, auto-vacuum pointer maps, overflow chains, reserved regions, rootless schema objects, and shadow tables. Expected behavior is asserted as graph facts and relationships, not as parser call sequences.
- A damage corpus covers truncated headers and pages, impossible geometry, out-of-range pointers, malformed varints, invalid cell extents, overlapping cells, cycles, duplicate and conflicting role claims, broken freelist and overflow links, invalid pointer-map claims, unsupported serial types, and opaque content. Tests prove containment at the correct validation boundary and preservation of independently valid evidence and validated prefixes.
- Sidecar scenarios cover no sidecars, structurally valid and malformed WAL files, WAL plus SHM, rollback journals that do and do not satisfy supported hot-journal evidence, and sidecars changing during inspection. Assertions focus on disclosure, validation state, warnings, and the invariant that no sidecar changes the main-file page image.
- Snapshot tests modify or replace an accepted input during fast or deep inspection and assert invalidation, preservation of observed facts as diagnostic evidence, refusal of further enrichment, and absence of any claim that the result is coherent. Tests use controlled file synchronization rather than timing-dependent sleeps.
- Budget and cancellation scenarios stop page scans, B-tree traversals, linked chains, cell processing, payload reconstruction, and decoding at deterministic boundaries. They assert exact evaluated extent, stop reason, known or unknown remainder, and no corruption diagnostic caused solely by the stop.
- Large-file tests use generated and sparse multi-gigabyte fixtures plus constrained-memory execution to prove positional access, bounded resident memory, lack of whole-file buffering, complete unsampled traversal when budgets allow, and spill behavior that is invisible at the graph contract.
- Explicit-target disclosure tests search every broad graph response, progress event, diagnostic, log capture, URL, page/schema summary, and adapter list for seeded sensitive values and raw payload fragments. Only a correctly scoped selected-cell result may contain decoded typed values; failed decoding must still withhold raw bytes.
- Deep-inspection tests cover local payloads, multi-page overflow, broken and cyclic overflow chains, unsupported values, decode-byte limits, cancellation, concurrent requests, repeated targets, and requests against stale revisions or invalidated snapshots. They assert immutable prior revisions and stable entity identities.
- Semantic enrichment tests run with the optional helper succeeding, unavailable, timing out, exceeding limits, and encountering hostile schema declarations. Physical graph facts must be identical in every case; only permitted semantic metadata may differ, and no application table or extension code may execute.
- Adapter contract tests render the same prepared inspection graph through the web and terminal query surfaces and assert equivalent identities, evidence, diagnostics, sidecar warnings, coverage, revision, and disclosure decisions. Visual arrangement and input handling are then tested at each adapter boundary without duplicating parser assertions.
- Browser interaction tests cover the page atlas as the default route, complete mosaic navigation, page/schema/cell selection, schema-flow transitions, rootless objects, projection changes that preserve selection, diagnostic links, byte maps, sidecar warnings, progress-to-publication transition, deep-inspection pending/completed states, revision navigation, and inaccessible or stale selectors.
- Web security tests cover loopback default binding, explicit non-loopback binding and warning text, same-origin behavior, strict headers, non-cacheable responses, bounded inputs and outputs, absence of absolute paths, absence of external requests, and rejection of selectors from another session or snapshot.
- TUI interaction tests cover keyboard-only movement, schema and allocation entry points, enter/back navigation, active path display, diagnostics, help, explicit deep inspection, cancellation, revision changes, terminal resizing, and continued access to warnings and coverage. Tests assert visible behavior through a terminal harness rather than Crossterm internals.
- Packaging tests build the production artifact from pinned inputs, start both adapters from the single executable, verify embedded browser assets without a separate runtime, and exercise the private metadata-helper invocation boundary. The helper must not be exposed as a general SQL execution interface.
- Fuzzing targets every parser boundary and selector decoder with arbitrary inputs under finite budgets. Success means no panic, memory unsafety, uncontrolled allocation, unbounded recursion, or fabricated complete coverage; a diagnostic or bounded fatal result is acceptable.
- Differential fixtures produced by supported SQLite releases may help establish valid-format expectations, but SQLite query results are never the oracle for physical coordinates, damaged-file facts, or sidecar overlay behavior. Hand-constructed and mutation-based fixtures remain necessary for invalid states SQLite itself will not create.
- Current production prior art is intentionally absent because the main branch contains discovery artifacts only. Interaction expectations come from the throwaway navigation prototype and ADR-0015; architectural testing vocabulary and shared-graph precedent come from the CUBRID Volmap sibling. Neither source authorizes copying prototype implementation details into production.

## Out of Scope

- Inspecting a live, changing database; acquiring an atomic live snapshot; follow mode; or refreshing an existing snapshot in place.
- Applying WAL frames, checkpointing a WAL, replaying or rolling back journals, constructing the latest logical database image, or guaranteeing transaction consistency beyond the supplied frozen snapshot.
- Repairing, recovering, editing, vacuuming, or writing any inspected database or sidecar.
- Acting as a general SQL console, database browser, row browser, query planner, migration tool, or application-data export tool.
- Broad decoding, indexing, searching, summarizing, or exporting of application values, and any raw payload or hex-dump fallback.
- Executing arbitrary SQL, triggers, views, application-defined functions, extensions, or virtual-table modules from the inspected database.
- Decoding proprietary encryption, compression, custom-VFS layouts, or extension-owned reserved bytes beyond preserving supported opaque evidence.
- Authentication, authorization, TLS termination, multi-user hosting, an internet-facing service mode, persistent hosted links, telemetry, or external cloud services.
- Persistent inspection indexes across process sessions, mutable graph revisions, or stable URLs across different database snapshots.
- Pixel-for-pixel promotion of any throwaway prototype variant or forcing physical, semantic, and terminal workflows into a single layout.
- Premature extraction of a shared multi-engine Volmap parser or domain model.
- Fixed performance promises or guessed default resource thresholds before reproducible benchmark evidence exists.
- Additional adapters such as a public JSON/JSONL export format, static HTML report, desktop shell, or plugin API unless separately specified.

## Further Notes

- The canonical SQLite database-format reference defines the header, one-based page numbering, B-tree page regions, freelist, pointer-map, overflow, lock-byte, and record serial-type structures that the physical parser must implement: [SQLite Database File Format](https://www.sqlite.org/fileformat.html).
- WAL is persistent database state and can contain committed changes not yet checkpointed into the main file, which is why sidecar discovery must produce a prominent limitation rather than a silent overlay: [SQLite Write-Ahead Logging](https://www.sqlite.org/wal.html).
- The WAL-index or SHM file is a native-byte-order coordination and lookup cache that is not required for recovery, supporting the decision to report it as non-authoritative sidecar evidence: [SQLite WAL-mode File Format](https://www.sqlite.org/walformat.html).
- SQLite ordinarily detects and rolls back a hot journal before reading a database, whereas this inspector must remain read-only and preserve the main-file image; hot-journal evidence therefore changes disclosure, not bytes: [SQLite File Locking and Concurrency](https://www.sqlite.org/lockingv3.html).
- SQLite recommends treating database files from another security domain as suspect and constraining any SQLite-library processing. The direct parser, bounded work, disabled extension/module execution, fixed helper queries, and trusted-schema restrictions follow that threat model: [SQLite Defense Against the Dark Arts](https://www.sqlite.org/security.html).
- The repository currently has no production parser, inspection session, CLI, TUI, server, or frontend scaffold. Ticketing should therefore start with a thin end-to-end tracer bullet through the inspection-session seam and one minimal adapter path, then deepen format coverage and the validated workspaces incrementally.
- Any future decision that changes frozen-input semantics, main-file-only semantics, direct-parser authority, explicit-target disclosure, immutable revisions, local/path-private serving, large-file constraints, or the three-workspace direction requires a superseding ADR rather than an implementation shortcut.
